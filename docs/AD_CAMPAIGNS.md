# Рекламные кампании

## Модель данных

`ad_campaigns` хранит конфигурацию, `analytics_events` — неизменяемую историю показов и кликов, `ad_campaign_user_state` — оперативное состояние пользователя, `ad_user_category_state` — общий cooldown категории. Статистика строится из событий, а не из агрегатов строки кампании.

Кампании бывают системными (`is_system=true`) и кастомными. Категории: `yandex`, `internal`, `partner`, `custom`. Ключ `promo_key` уникален и состоит из строчных латинских букв, цифр и `_`.

## Триггеры и выбор

Схема допускает `download_count`, `activity_cooldown`, `combined` и зарезервированный `manual`. Временной триггер не является рассылкой по расписанию: после истечения ожидания кампания становится доступной и проверяется при следующем безопасном действии пользователя. Сейчас автоматические точки входа — успешное завершение загрузки и возврат в главное меню. `manual` исключён из автоматического выбора, помечен в админке как недоступный и отклоняется сервером до появления отдельного API отправки.

Перед показом проверяются активность, архив/удаление, период действия, условие загрузок, персональный cooldown, cooldown после клика, общий cooldown категории, максимум показов и факт показа в текущей сессии. Из доступных кампаний выбирается одна с учётом `weight`.

Redis-ключ `promo-session-shown:<userId>:<sessionId>` с TTL 1800 секунд не допускает вторую рекламу в сессии. При недоступном Redis используется память процесса, поэтому строгая межэкземплярная гарантия в этом режиме отсутствует.

## Показ и клик

Сначала Telegram успешно отправляет обязательные сообщения, затем RPC `record_ad_campaign_impression` атомарно создаёт `yandex_promo_shown` и обновляет пользовательское и категорийное состояние. Ошибка Telegram не считается показом.

Первое нажатие callback-кнопки вызывает `record_ad_campaign_click`. Дедупликация по пользователю, кампании и `message_id` запрещает повторный клик; после записи кнопка заменяется на понятную URL-кнопку, а callback сообщает, что для перехода нужно нажать ещё раз.

В `event_data` сохраняются `campaign_id`, `promo_key`, `campaign_name_snapshot`, `message_id`, `placement`, `url_hash`, `trigger_download_count`, `impression_number`, `trigger_type`, `days_since_previous_impression`, `user_session_id`, `has_media`, `media_type` и `creative_variant`.

## Медиа

Файлы находятся в приватном Supabase Storage bucket `ad-campaign-media`; постоянные публичные URL не сохраняются. Поддержаны JPEG, PNG, WEBP, GIF до 10 МБ и MP4 до 20 МБ. Тип определяется по содержимому файла; SVG и HTML отклоняются.

Изображения отправляются через `sendPhoto`, GIF — через `sendAnimation`, видео — через `sendVideo`, кампания без медиа — через `sendMessage`. Для длинного текста отправляется медиа с короткой подписью и отдельное обязательное сообщение с кнопкой. Показ фиксируется только после успеха всей обязательной последовательности.

При замене сначала загружается новый объект и сохраняется кампания, затем старый объект удаляется, если на него больше нет ссылок. Ошибки компенсируются насколько возможно и журналируются; PostgreSQL и Storage не образуют общей транзакции, поэтому эксплуатационный контроль ошибок обязателен.

## Жизненный цикл

Кастомную кампанию можно выключить, архивировать, восстановить и мягко удалить из архива с подтверждением имени. Системную можно редактировать, включать/выключать и сбрасывать, но нельзя удалить. Обычный выбор требует `is_active=true`, `is_archived=false`, `deleted_at IS NULL`.

История `analytics_events` и состояния пользователей при архивировании и удалении не очищаются. Медиа при архивировании сохраняется; при удалении удаляется только объект без других ссылок. Изменения пишутся в `ad_campaign_audit_log`.

Защищённые методы: `POST /admin/api/ad-campaigns/:id/archive`, `/restore`, `/reset` и `DELETE /admin/api/ad-campaigns/:id`.

## Статистика

RPC `get_ad_campaign_stats` возвращает показы, уникальные показы, клики, уникальные клики, CTR, повторы, среднее число показов и последние даты. Дополнительные RPC группируют показатели по медиа/`creative_variant` и типу триггера. Dashboard формирует строки динамически из `ad_campaigns` и `analytics_events`; legacy-счётчики показываются отдельно и не подменяют событийную статистику.
